# Production cutover

Preparation only. Merging this procedure does not deploy production. Production approval and develop acceptance must identify the final release commit. Future Source Document publication and PDF removal remain separate operations; they do not block the as-is legacy copy or its display.

## Before mutation

Record explicit user acceptance of the exact develop commit and its complete #65 report. Record explicit production-deployment approval for that same commit. Agree a dated rollback deadline. Copy the [record template](../data/release/production-cutover.example.json) to an ignored private location and fill references from actual evidence. A filled JSON file is evidence routing; it does not grant permission by itself. Pending source dates, acquired-byte paths and R2 mappings apply only to future publication as reviewed Source Documents. Preserve existing data and PDF URLs without inventing those facts.

Verify production Turso, document R2, backup R2 and private Source Tips identifiers against staging. Use separate databases, buckets and credentials. Set whole-bucket **indefinite** locks on both production document and backup buckets before import, then read the rules back from Cloudflare. Native API locks can be administered later; retain the rule evidence and access controls. Restrict production public runtime to Archive database reads and document object reads. Keep operator writes out of Netlify. Builds never mutate data.

Run the verifier from the clean checkout at the exact accepted commit. It rejects modified or untracked source files and a different HEAD. Keep private records and dumps in ignored locations. Install a `sqlite3` CLI version 3.40.1 or newer with `-safe` support before running it. Restoration uses native safe mode in a temporary directory, rejects filesystem modules and non-dump PRAGMAs, requires the dump to end its transaction, and reopens the persisted database before checking it. A restore that exceeds 60 seconds fails closed and needs a separately reviewed recovery procedure.

Before accepting the release commit, review and commit the production libSQL URL as `productionTursoDatabaseUrl` in `data/release/stage-one.json`. Its current `null` value keeps production verification blocked until the target is approved. Copy that exact URL to `targets.tursoDatabaseUrl` and `TURSO_DATABASE_URL`, and set a production read-only `TURSO_AUTH_TOKEN` in the private operator shell. The verifier binds both operator values to the release plan in the accepted clean checkout. Also review and commit `stagingTursoHost` in that plan. Its current `null` value blocks verification. The production host must differ from this independently reviewed staging hostname. Operator environment values cannot replace it. It reads the database in one transaction and compares the restored schema and all table contents, including non-public records and the migration ledger. A matching public snapshot alone is insufficient.

Also review and commit `productionR2` with the approved `accountId`, `documentBucket`, `documentJurisdiction`, `backupBucket` and `backupJurisdiction` in that release plan. Its current `null` value blocks verification. The private record must name those exact identifiers. Document and backup buckets must be distinct `(bucket name, jurisdiction)` pairs; equal names in different jurisdictions identify separate buckets. Each jurisdiction must be explicit: `default`, `eu`, `us` or `fedramp`. Lock reads send each bucket's jurisdiction header, and backup reads use its jurisdiction-specific S3 endpoint. Unsupported jurisdictions fail closed. Also review and commit `stagingR2` with its `accountId`, `bucket` and `jurisdiction` in the accepted release plan. Its current `null` value blocks verification. This complete staging identity must come from the independently reviewed plan, not operator environment values. A matching name in a different account or jurisdiction is separate. A missing or invalid identity blocks verification because separation is unproven. The verifier rejects the same resource before it reads any lock or backup object. Credentials remain private.

## Backup and import sequence

1. Stop competing editorial imports. Take an immediate live Turso **SQL dump** through the native `turso db shell <production-database> .dump` command into a new private file. Do not use `turso db export` as this SQL recovery artifact: that command produces a SQLite generation snapshot and its documentation warns that it may lag recent changes. Record the dump checksum and time. Keep all SQL dumps private.
2. Restore the pre-import SQL file into a fresh local database and require SQLite integrity success. Upload the exact file to a new release-scoped key in the locked backup bucket. Read it back and compare bytes and SHA-256. Never overwrite a recovery point.
3. Run `npm run archive:verify-recovery -- <private-cutover-record.json> before <accepted-commit>`. The command checks references, the exact accepted snapshot, live whole-bucket indefinite locks, SQL restoration and the exact locked backup object. It writes a private `<private-cutover-record.json>.before.json` report only after every check passes. Keep it beside the cutover record. The report binds the accepted revision, database, backup bucket identity, pre-import object key/checksum and live database digest. It uses exclusive creation with mode `0600`; an existing report is never overwritten. Use a new cutover-record filename for a new verification run. The command performs **reads only** against providers. It does not publish Source Documents and does not require future editorial work to be complete. `R2_CONFIG_READ_TOKEN` reads lock configuration; `BACKUP_R2_ACCESS_KEY_ID` and `BACKUP_R2_SECRET_ACCESS_KEY` read only the backup bucket.
4. Apply the accepted migration through the approved production operator operation. Follow [Copy and verify](legacy-migration.md#copy-and-verify) to preserve the complete public Firebase collection in the named production database. Compare every typed field, profile and SALN entry count; verify an identical replay adds no rows. Keep all existing `public/saln/` files at their original URLs and verify their bytes. Apply the separate accepted reviewed release only within its approved scope. Any new reviewed Source Document needs its manifest evidence and acquired bytes before publication. The generic staging CLIs continue to reject production; use the shared migration/import functions only in the authorized operator operation, and do not relabel production as staging.
5. Take the immediate post-import SQL dump. Restore it and require the accepted public snapshot version and the `legacyCapture` checksum and counts in the committed release plan. The verifier recomputes the checksum from every stored typed field in the active legacy capture and counts its profiles and SALN entries. The accepted copy has 49 profiles and 129 SALN entries. A missing, changed or partial copy fails even if the reviewed snapshot matches. An older complete capture cannot hide a newer partial capture selected by the runtime. Store a new locked `post.sql` recovery point and compare readback bytes and checksum. Run the verifier with `after` using the same cutover-record filename; it requires both recovery artifacts and the successful `.before.json` report. A missing report or a mismatched revision, database, bucket, pre-import key or checksum stops verification. Before import, the pre artifact must match the live production database; afterward, the post artifact must match it. The after check also restores and reads back the retained pre artifact and compares it with the database digest saved by the before check. A partial import or failed backup stops promotion.
6. Promote only the accepted develop state to main after explicit promotion/deployment approval. Set production reads to `ARCHIVE_ADAPTER=turso`, named production Turso, and `ARCHIVE_STORAGE=r2`. Use one metadata authority and no Firebase dual writes. Keep Firestore unchanged throughout the agreed rollback window. Do not run old Firestore migration/deploy commands.

## Verification and recovery

Record the actual Netlify deploy ID, exact SHA, resources, migration ledger, manifest digests, snapshot/checksum versions and locked recovery keys/hashes. Run #65 HTTP checks against production and repeat browser journeys, private Source Tip verification and network inspection. Verify stable profile/PDF routes, source open/download bytes and no Firebase calls. Provider limits for buffered document responses must be exercised with representative large exact files before acceptance.

If cutover fails, stop writes and retain all failure evidence. Restore the prior deployment/configuration during the agreed window; Firestore remains untouched. Never overwrite or delete locked documents to roll back metadata. Restore database state only through a separately approved recovery operation. After successful verification, report the result and recovery points to the user. Destructive cleanup remains deferred until the agreed window ends and replacement document access is proven. The Turso runtime code can merge while original PDFs remain in place. Remote Firestore deletion is a separate decision.
